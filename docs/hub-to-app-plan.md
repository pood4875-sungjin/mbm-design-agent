## 0. 결론 5줄
1. **hub 와 앱은 문서 모델이 다르다.** hub 는 「페이지›프레임›레이어」를 직접 들고 있는 편집기(레이어가 곧 데이터), 앱은 「캠페인 brief·style + 소재별 overrides → 렌더러가 매번 다시 그림」. 그래서 hub 컨트롤은 **그대로 옮기지 말고 overrides 키로 번역**해야 한다(표 2의 「옮길 방법」 칸).
2. **이미지 바꾸기는 데이터 경로가 이미 반쯤 있다.** `generate.js`·`adEffStyle` 가 `{...c.style, ...a.overrides.style}` 로 합치므로 `overrides.style.keyVisual/kvMeta/logo` 만 넣으면 그 소재만 다른 그림으로 다시 그려진다. 막히는 건 ① `kvVariants`(가로/세로형)가 덮어쓰는 순서 ② 소재마다 data URL 을 저장하면 IndexedDB 가 커지는 것 — 둘 다 1단계에서 해결.
3. **오른쪽 「선택 없음」은 이미 hub 와 내용이 거의 같다**(비주얼·로고·배경·컬러·글자·검수). 빠진 건 색 스타일 이름/추가, 내보내기 칸(배율·범위), 도구(다시 생성·보드 정리·룰러) 와 **hub 식 섹션 문법**(40px 머리 · `+` 버튼 · 행 32). 이동·정리 위주라 위험이 낮다.
4. **요소(이미지) 패널이 가장 큰 공백**: 앱은 X·Y·W·H + 「키비주얼 바꾸기 → 전체 일괄로 이동」뿐. hub 의 정렬·회전·뒤집기·불투명도·모서리·혼합·채움(이미지 바꾸기·맞춤)·선·효과 중 **렌더러와 안 부딪히는 것(채움 바꾸기·맞춤·불투명도·모서리·뒤집기·정렬)부터**, 녹임·스크림과 부딪히는 것(회전·혼합·효과)은 뒤로 미루거나 잠근다.
5. **스타일은 hub 의 ui3 토큰으로 수렴**: 앱 작업 화면은 이미 입력 칸 r5/32px·세그먼트를 옮겼지만, 패널 폭(256/288 vs 284/248)·섹션 머리(12.5px 굵게 vs 12px 600 · 40px)·파랑 포커스(#2f6fed vs #0D99FF)·떠 있는 툴바·왼쪽 레일이 다르다. 토큰 14개(§4)만 맞추면 대부분 정리된다.

## 3. IA 안

원칙: **왼쪽 = 무엇을(내용·재료), 오른쪽 = 어떻게(선택한 것의 모양)**. 오른쪽은 선택 단위 3단계(없음 → 소재 → 요소)로 바뀌고, 맨 위 「전체 일괄 / 이 소재만 / 이 요소만」 범위 표시(현행 `scopeHtml`)는 유지 — hub 엔 없지만 앱의 overrides 층을 사용자에게 보여 주는 유일한 장치라 빼면 안 된다.

## 5. 구현 순서(단계마다 커밋 가능, 이미지 바꾸기부터)

| 단계 | 내용 | 바뀌는 파일 | 테스트 | 크기 |
|---|---|---|---|---|
| **1. 이 소재만 그림·로고 바꾸기** | 요소(키비주얼) 패널에 「채움」 섹션: 썸네일 · 맞춤(자동/전체/칸 안 → `kvUse` auto·full·part) · 🖼 바꾸기(파일) · 「이 소재 색도 맞춤」 체크 · 「전체 키비주얼로 되돌리기」. 저장 = `overrides.style.{keyVisual, kvOrig, kvMeta, kvVariants:null}` (+ AI 조각 제거), 그림은 `c.assets[hash]` 한 번 + 참조. 로고 요소도 같은 모양(`logo/logoLight/logoMeta/logoTone`). 캔버스에 파일 끌어 놓기 = 놓은 소재의 그림 바꾸기 | app/app.js(요소 패널·bind), core/generate.js·adEffStyle(참조 풀기), core/assetref 또는 campdb(자산 저장) | 새: override KV 가 그 규격만 바꾸고 kvVariants 무시 · 다른 규격 바이트 동일 · 저장 크기(같은 그림 두 소재 = 1번 저장) · 되돌리기 1걸음 | M~L |
| **2. 이미지 외관** | 불투명도(칸+슬라이더+눈) · 모서리 · 뒤집기(누끼만, 사진형은 잠금+이유) · 정렬 6 · 비율 고정. 저장 `overrides.elements.kv.{op,hid,r,flip}` → elementedit 이 data-object 묶음에 적용 | core/elementedit.js(+정규화), app/app.js, app/elselect.js(크기 배지) | element-edit 테스트에 kv op/r/flip, 녹임 층 함께 적용, SVG 내보내기 충실도 | M |
| **3. 오른쪽 「선택 없음」 hub 섹션 문법** | 페이지(캔버스 색 이동) · 키비주얼·지면(비주얼+배경 합침) · 스타일(3색 행 + 사용자 색) · 전체 글자 · 내보내기(배율·범위) · 도구(규칙대로 다시 그리기·룰러) · 대화로 시안 · 매체 추가. 섹션 머리 40/600 + `+` 아이콘 | app/app.js(renderInspectorBody 선택 없음 분기), app/index.html CSS | 기존 인스펙터 테스트 id 유지(iKv·iKvFile·iColor1…) — id 바꾸지 않기 | M |

순서 근거: 사용자가 「이미지 바꾸고 하는 기능부터」라고 했고, 1·2 는 데이터·렌더 쪽이라 다른 에이전트의 app.js UI 개편(왼쪽 브리프·글자 패널)과 부딪히는 면이 작다. 3~5 는 같은 파일의 큰 마크업을 건드리므로 그 둘이 끝난 뒤.

## 6. 정해야 할 것
1. **이 소재만 그림을 바꿨을 때 색**: 기본 「그 소재 색도 새 그림에 맞춤」(hub 동작) vs 「캠페인 색 유지」(브랜드 일관). 제안: 유지 + 체크박스.
2. **주 버튼 색**: hub 파랑(#0D99FF) vs 앱 잉크 검정. 제안: 포커스·선택은 파랑, 주 버튼은 「내보내기」만 파랑.
3. **사진형 KV 회전·뒤집기**: 잠금(제안) vs 녹임 층까지 같이 변환(L 난이도).
4. **혼합 모드·효과·선**: 넣지 않음(제안) vs 2차.
5. **패널 폭**: hub 그대로 284/248 이면 오른쪽 글자 패널(2열 칸)이 좁아짐 — 264 절충?
