# MBM Design Generator — PRD

- **작성일**: 2026-08-10
- **상태**: 개념 합의 v1 (그릴 인터뷰 완료, [CONCEPT.md](CONCEPT.md) 결정 14개) → **개발 착수 전**
- **한 줄**: MBM 기획을 대화로 입력하면, 하나의 **Campaign Context**(정보)와 **Campaign Style**(표현)로 온·오프라인 전 채널 디자인 산출물을 자동 생성·베리에이션하고, 실행 가능한 출력 포맷(이메일 HTML·랜딩 패키지·배너 이미지·인쇄 PDF)까지 뽑는 AX 디자인 에이전트.

---

## 1. 배경 · 문제

하나의 MBM 캠페인에서 디자이너는 eDM·랜딩·배너·SNS·PPT·포스터·X배너를 **각각** 제작한다. 동일한 기획을 매체마다 반복 해석하고, 일정·장소·연사가 바뀌면 이미 만든 산출물을 하나씩 찾아 수정하며 누락을 재확인한다. 창의적 판단보다 반복 제작·수정·운영에 시간이 소모된다.

**전환**: 디자이너가 N개 결과물을 만드는 사람 → **캠페인 디자인 시스템 하나를 설계·판단하고 AI로 확장하는 사람.**

## 2. 최종 모습 (Vision)

- **파일럿 (4~6주)**: 디자이너 단독 사용. 실제 MBM 1건 — 기획 입력 → Context → Style → eDM·랜딩·배너 2~3규격·포스터/X배너 생성 → 실행 포맷 파일. 직전 MBM 재현으로 검증 후 예정 MBM 실전 투입.
- **최종상**: 요청자(사업/마케팅)가 직접 브리프 입력, 디자이너 승인 게이트. 전 채널(SNS·PPT·Signage). Direction 3경로(디자이너 제공·프리셋·AI 생성). HubSpot API 자동 등록. KPI 로그 = 운영 대시보드.

핵심 불변식 (설계 기준은 최종상, 파일럿은 부분집합):

1. **정보는 시스템 소유, 표현은 디자이너 소유.** Context 정보(일시·장소·연사·CTA)는 전파가 갱신하고, 디자이너가 손댄 스타일·레이아웃은 보존한다. 충돌 시 목록으로 확인.
2. **입력 경로가 무엇이든(업로드·프리셋·AI 생성) Campaign Style 하나로 정규화된다.** 전개 엔진은 하나.
3. **빈칸은 추측하지 않는다.** 없는 정보는 되묻는다.
4. **모든 산출물 확정은 디자이너 승인 게이트를 거친다.**

## 3. 목표 · KPI

| KPI | 정의 | 목표 |
|-----|------|------|
| **1. 캠페인 디자인 제작시간** | MBM 기획 확정 → 산출물 제작 완료까지 디자이너 실투입 시간 | **60%+ 단축** |
| **2. Variation AI 수행률** | 분모 = 산출물 종수 × 채널별 규격 수. 디자이너 개별 재디자인 없이 Agent가 생성·변형한 비율 | **80%+** |

Baseline: 파일럿 전 1주 신규 측정 + 직전 MBM 1건 회고 측정 병행.

## 4. 사용자 · 역할

| 역할 | 하는 일 | 파일럿 | 최종상 |

| **요청자** (사업/마케팅) | 브리프 입력 · 정보 변경 전달 | 기존 채널로 자료만 전달 | 대화창 직접 입력 |

## 5. 사용자 플로우

> 시각 자료: [proposal.html](proposal.html) 플로우차트 2종 · Figma Design Generator p.18

**생성 플로우** (사람→AI→시스템):
진입(대화창) → 기획 입력(자연어/PPT/워드) → 생성 항목 선택(온라인: eDM·랜딩·홍보배너 / 오프라인: X배너·현수막·포스터) → 필요 항목 추가 입력(에이전트가 되물음) → 그래픽 가이드 입력(키비주얼·컬러·폰트·로고) → **자동 생성** → 결과 리뷰(아니오 = 수정 지시·재생성 루프 / 예 = 승인) → 채널 분기 → 온라인 포맷 / 인쇄 포맷 → 산출물 전달. 점선(추후): 키비주얼 AI 생성, HubSpot 자동 등록.

**자산 검색 플로우** (재사용 진입점):
자연어 질문("작년 온사이트 출시 MBM 배너 찾아줘") → AI 조건 해석(연도·브랜드·산출물) → 시스템 필터 서칭 → 사람 미리보기 확인(아니오 = 조건 바꿔 재검색) → 원본 접근(다운로드·Figma·NAS) → 재사용.

**변경 전파 플로우**:
"장소가 킨텍스로 변경됐어" → 영향 산출물 목록(손편집 표현 유지 표기) → 일괄 반영 → 재승인.

## 6. 기능 요구사항

### P0 — 파일럿 범위

| # | 기능 | 내용 |
|---|------|------|
| F1 | **대화 입력·파싱** | 자연어 + PPT/워드 첨부 → 행사 정보 추출, Context 초안 생성 |
| F2 | **Campaign Context** | 코어 필드(행사명·일시·장소·타깃·CTA) 고정 + 채널별 필드는 산출물 선택에 따라 확장. 빈칸 = 되묻기(추측 금지). Context 카드로 확인·수정 |
| F3 | **산출물 선택** | 온라인(eDM·랜딩·홍보배너) / 오프라인(X배너·현수막·포스터) 체크 → 채널별 필드·규격 결정 |
| F4 | **Campaign Style** | 키비주얼 업로드 + 컬러·폰트·로고 입력 → 정규화(키비주얼·팔레트·타이포·무드). **프리셋 서랍**: 완료 캠페인 스타일 저장·재사용 |
| F5 | **자동 생성** | Context + Style → 채널 렌더러가 전 산출물 Variation. 비율 대응 = 안전 크롭 + 색면 배경 확장 |
| F6 | **리뷰 루프** | 대화 지시 = 전 산출물 일괄 재생성, 직접 편집 = 개별 예외(data-edit 방식). 전체 승인 |
| F7 | **변경 전파** | Context 수정 → 영향 목록 → 일괄 반영. 불변식 1 적용(정보 갱신·표현 보존·충돌 확인) |
| F8 | **출력** | eDM = 이메일 호환 HTML(테이블·인라인 CSS·600px), 랜딩 = 자기완결 HTML 패키지, 배너 = PNG/JPG 규격별, 오프라인 = 인쇄용 PDF(재단 여백 포함) |
| F9 | **자산 검색** | 자연어 → 조건 해석 → 캠페인·산출물 필터 → 미리보기 → 원본 접근 |
| F10 | **KPI 로그** | 캠페인별 산출물 수·Variation 수·수정 지시·재생성·리드타임 자동 기록 (§11) |

## 7. 데이터 모델

```
Campaign
├─ context: CampaignContext        ← 정보 (시스템 소유)
│   ├─ core { 행사명, 일시, 장소, 타깃, CTA, ... }
│   ├─ channelFields { edm:{발신자,제목}, landing:{폼항목}, print:{규격}, ... }
│   └─ version                     ← 전파 추적
├─ style: CampaignStyle            ← 표현의 원본
│   ├─ keyVisual (이미지)
│   ├─ colors · fonts · logo · mood
│   └─ presetId?                   ← 프리셋 서랍 출처
├─ artifacts: Artifact[]
│   ├─ channel · spec(규격)
│   ├─ doc (콘텐츠 슬롯 — Context에서 파생)
│   ├─ overrides (디자이너 손편집 — 표현, 전파에서 보존)
│   ├─ status: draft → review → approved
│   └─ outputs (html/png/pdf 경로)
└─ log: ActivityLog[]              ← KPI 원천
```

전파 규칙 구현: `doc`은 Context 버전에서 재파생(시스템 소유), `overrides`는 필드 단위 보존(디자이너 소유). 같은 필드 충돌 = 확인 큐.

## 8. 아키텍처 원칙

1. **onsite-web-generator 선별 이식** — 팩 계약 개념(토큰 정규화 → Campaign Style), llm 호출 패턴(llm.js), 렌더러·data-edit 패턴만. 통째 포크 금지.
2. **채널 렌더러 = 계약** — 모든 렌더러는 (Context, Style, spec) → HTML을 받는 동일 인터페이스. 채널 추가 = 렌더러 1개 추가.
3. **HTML이 단일 소스** — 모든 산출물은 HTML로 렌더 후 채널별 변환(이메일 HTML 변환 / 이미지 캡처 / 인쇄 PDF). onsite에서 검증된 경로.
4. **앞문 교체 가능** — 파일럿 입력은 대화+업로드, 추후 요청자 입력·AI 생성이 와도 Context/Style 구조는 불변.

## 10. 비기능 요구사항

- **이메일 호환**: Outlook·Gmail·모바일 클라이언트 렌더 검증 (파일럿 중 실발송 테스트 1회)
- **인쇄 품질**: 실측 mm 규격 → 300dpi 래스터 또는 벡터 PDF, 재단 여백
- **생성 시간**: 전 산출물 생성 수 분 이내 (대화 흐름 안에서 대기 가능한 수준)
- **자기완결 산출물**: 외부 의존 없는 파일 — 어디든 전달·배포 가능 (onsite 원칙 계승)
- **로컬 우선**: 파일럿은 백엔드·계정 없이 동작 (onsite와 동일 배포 모델)

## 11. KPI 측정 설계

이벤트 로그 (자동): `campaign_created` · `context_confirmed` · `artifact_generated` (채널·규격) · `revision_requested` (대화 지시) · `manual_edit` (직접 편집) · `propagation_run` (변경 전파, 영향 수) · `artifact_approved` · `export_done` — 각 타임스탬프 포함.

- KPI 1 = (기획 확정 → 전체 승인) 구간의 디자이너 실투입 시간 (수동 보정 허용)
- KPI 2 = artifact_generated 중 manual_edit 없이 approved된 비율 / 전체 (종수 × 규격)

## 13. 열린 질문

1. **예정 MBM 날짜** — 나오면 W6 역산으로 일정 재배치
2. **직전 MBM 기획자료 샘플** — W1 착수 조건
3. **배너·인쇄물 실규격** — 실제 발주 이력 기준으로 §9 확정
4. **앱 형태** — 대화 UI를 어디에 얹나: onsite studio식 로컬 웹앱(기본 가정) vs 별도 클라이언트. W1에서 결정
5. **저장 방식** — 파일 기반(캠페인 폴더) vs localStorage. 자기완결 원칙상 파일 기반 우선 검토
6. **HubSpot 토큰** — P1 대비 미리 발급 요청만 넣어둘지
